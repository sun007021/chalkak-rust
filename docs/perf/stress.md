# 스트레스 시험 (트래픽이 몰릴 때의 서버·풀 안정성)

이슈 #36. Java(Tomcat NIO + HikariCP)와 Rust(연결마다 OS 스레드 + 실행 세마포어 + 고정 풀)에 **같은 조건**으로 몰리는 트래픽을 보내
오류·지연·자원 누수를 비교한다. 일반 비교(`bench`)·동시성(`race`)·장시간(`soak`)과 달리 **서버가 한계를 넘는 순간과 그 뒤의 회복**을 본다.
부하 발생기 명령은 `chalkak-loadgen stress`, 실행은 `harness/scripts/perf.sh stress`다. 결과는 `$PERF_OUT/stress-<java|rust>.json`이고
`perf.sh report`가 표로 읽는다.

## 두 구현의 구조 (시험이 겨냥하는 차이)

| | Java | Rust |
| --- | --- | --- |
| 연결 받기 | Tomcat NIO 폴러. 스레드는 요청이 있을 때만 쓴다. `max-connections` 8192, `accept-count`(리슨 백로그) 100 | accept 루프 1개가 연결마다 OS 스레드를 띄운다(`serve.rs` 109~126행). 연결 한도 8192. 리슨 백로그는 `std` 기본 128 |
| 요청 실행 동시 수 | 워커 스레드 최대 200 | 세마포어 200(`Gate`, `serve.rs` 135~170행). 요청을 다 읽은 뒤에야 자리를 잡는다 |
| 유휴 keep-alive 연결 | 스레드를 안 쓴다 | 스레드 1개(+FD 1개)를 쓰고 요청이 올 때까지 잠든다(#36 이전: FD 2개, 100ms마다 깨어남) |
| DB 풀 | HikariCP 10, 대기 30초, 연결을 백그라운드로 채운다 | `Mutex`+`Condvar` 고정 10(`pool.rs`), 대기 30초, 연결을 버리면 백그라운드로 다시 채운다(#36 이전: 필요할 때만) |
| 요청 읽기 제한 | `connectionTimeout` 60초 | `read_timeout` 20초(바이트가 오면 갱신), 유휴 `keep_alive_timeout` 60초 |

## 실행

```bash
harness/scripts/perf.sh up                          # 스택(Java, Rust, 각자의 PostgreSQL)
harness/scripts/perf.sh stress both                 # 8개 케이스 전부, Java와 Rust
harness/scripts/perf.sh stress rust spike:200       # 케이스[:크기]. 크기를 주면 그 크기만
harness/scripts/perf.sh stress java storm
harness/scripts/perf.sh report                      # $PERF_OUT/report.md 의 "스트레스 시험" 표
```

| 환경변수 | 뜻 |
| --- | --- |
| `PERF_STRESS_QUICK=1` | 시간을 3분의 1로(스모크). 느린 클라이언트 시험의 제한 시간 대기는 줄이지 않는다 |
| `PERF_STRESS_RPS` | 유휴·느린 연결·끊기 시험의 기준 부하(고정 RPS, 기본 60) |
| `PERF_PG_PERSIST=1` | DB 데이터를 tmpfs 대신 볼륨에 둔다(`harness/perf/compose.persist.yaml`). **DB를 stop/start하는 `outage` 시험에 필요**하다. tmpfs는 컨테이너를 멈추면 사라진다. 이 변수 없이 `stress`를 돌리면 outage는 pause만 한다. 스택을 띄울 때와 내릴 때 같은 값을 써야 볼륨이 지워진다 |
| `PERF_APP_NOFILE`, `PERF_APP_PIDS` | 앱 컨테이너의 nofile·pids 한도(`compose.limits.yaml`). 한도에서 무엇이 먼저 막히는지 볼 때 쓴다. 스택을 다시 띄워야 적용된다 |
| `PERF_STRESS_OUTAGE_MODE` | `pause`, `stop`, `both` |

`perf.sh stress`는 컨테이너의 브리지 IP로 서버에 붙는다(호스트 포트의 docker-proxy를 거치지 않는다: 연결 폭주가 docker-proxy의 큰 백로그가 아니라
서버 자신의 리슨 큐를 보게 한다). 부하 발생기 `ulimit -n`은 하드 한도까지 올리고, 스레드 스택은 128KB로 줄였다. 부하 발생기가 열 소켓 수
+ 256보다 `nofile`이 작으면 시작하지 않고 "부하 발생기 쪽 한도"라고 실패 사유를 적는다.

직접 부를 때:

```bash
target/release/chalkak-loadgen stress --case spike:400 --base 172.18.0.5:8080 --secret <hex> --db "<접속 문자열>" \
    --label rust --container <앱 컨테이너 ID> --db-container <DB 컨테이너 ID> --out stress-rust.json [--quick] [--sizes 50,200]
```

`--label`이 `java`를 포함하면 Java 기준(느린 클라이언트 60초, 스레드 상대 비교), 아니면 Rust 기준이다. `--container` 대신 `--pid`도 된다.
`--db`로 부하 발생기가 DB에 여는 연결은 `application_name=chalkak-loadgen`을 달아서 앱 연결과 구분한다(누수 검사·연결 끊기에서 제외).

## 누수 검사 (모든 케이스의 끝)

케이스 시작 전과 끝(최대 20초까지 1초마다 다시 본다)을 비교한다. 하나라도 어기면 그 케이스는 실패다.

| 항목 | 기준 |
| --- | --- |
| 앱 DB 연결 수(`pg_stat_activity`, 부하 발생기 제외) | 풀 크기(10)와 **같다** |
| `idle in transaction`(중단된 것 포함) | 0 |
| 앱 스레드 수 | Rust: 시작 +8 이내. Java: 시작 +210 이내(JVM 스레드라 상대 비교. Tomcat 워커 최대 200이고 유휴 워커는 60초 뒤 줄어든다) |
| 앱 FD 수 | 시작 +16 이내 |

끊기·중단 케이스는 먼저 동시 요청 64개로 풀을 채운 뒤 센다. 죽은 연결은 빌릴 때 검사해서야 드러나므로, 저부하에서는 앱이 버리기 전까지 풀 안에 남아 있다(두 구현 모두).
채우기 전 연결 수는 `extra`에 따로 남긴다(`app_conns_low_load_end`).

## 케이스

모든 부하는 `mix.rs`의 일반 혼합(읽기 약 86%, 쓰기 약 14%)이다. 따로 적은 것만 다르다. 요청 시간은 풀 대기까지 포함한다.

| 케이스 | 절차 | 판정(통과 기준) |
| --- | --- | --- |
| `spike[:N]` N=50, 200, 400, 800 | 낮은 부하(연결 8, 40 req/s 고정) 8초 → 연결 N개가 keep-alive 최대 처리량으로 20초 → 다시 낮은 부하 15초. 낮은 부하 요청은 계속 흐르며 1초 창별 p99를 남긴다 | 세 구간 모두 오류 0(연결 실패·RST·타임아웃·5xx·4xx), 급증이 끝난 뒤 낮은 부하 p99가 `max(기준선x3, 기준선+50ms)` 이하인 창이 연속 3개가 되기까지 10초 이내. 풀 대기는 앱이 노출하지 않아 급증 구간 최대 지연을 상한으로 적고, DB 세션이 풀 크기 이상 활성인 표본 비율(`pool_saturated_ratio`)을 함께 적는다 |
| `storm[:N]` N=1000, 3000 | keep-alive 없이 N개를 거의 동시에 열고(출발 신호로 한꺼번에) 가벼운 `GET /actuator/info` 하나씩. 연결 10초·응답 30초 제한 | 성공 비율 N≤1000이면 99%, 그 이상이면 95% 이상, 폭주 뒤 서버가 바로 응답. 서버 netns의 `ListenOverflows`/`ListenDrops` 증가분을 `extra`에 남긴다 |
| `idle[:N]` N=2000, 5000 | 유휴 연결 없이 CPU 기준선 → 일반 부하(고정 60 req/s) → N개를 하나씩 맺고 keep-alive로 붙여 둔 채(20초마다 한 번 요청해 제한 시간 회피) 서버 CPU(유휴만) → 같은 일반 부하 | N개가 모두 붙고, 부하 중 오류 0, p99가 `max(없을 때x2, +100ms)` 이하, 유휴 연결만으로 서버 CPU 0.5코어 이하, 서버가 끊은 연결 0. `cpu_cores_per_1000_idle`이 유휴 연결 1000개당 CPU. 실패하면 원인(부하 발생기 nofile / 서버 nofile / 서버 pids / 그 밖)을 가려 적는다 |
| `slow[:N]` N=400 | 일반 부하 10초 → N개 느린 연결: 1/4은 헤더 앞부분만 보내고 멈춤(stalled), 3/4은 헤더를 3초에 한 바이트씩(drip). 서버 제한 시간(Rust 20초, Java 60초) + 10초 동안 붙들고 일반 부하를 계속 본다 | 일반 부하 오류 0, p99가 `max(기준선x3, +100ms)` 이하, 멈춘 연결은 모두 제한 시간 + 5초 안에 서버가 끊음(응답 코드는 기록: Rust는 408, Java는 조용히 닫음). drip은 판정하지 않고 기록한다(아래 발견 참고) |
| `fairness[:N]` N=400, 1000 | 연결 N개가 DB를 쓰는 `GET /api/v1/posts/today` 하나만 30초 동안 최대 처리량으로 | 오류 0(풀 대기 30초를 넘긴 500 포함), 연결별 완료 수의 최소/중앙값 0.2 이상(굶는 연결 없음), 최대 지연 30초 미만. p99.9, 1·5·10초 넘은 요청 수도 기록 |
| `dbkill` | 일반 부하(연결 16, 60 req/s) 중 `pg_terminate_backend`로 앱 연결을 모두 끊기, 10초 간격으로 3번 | 라운드마다 오류가 (풀+연결 수=26) 이하이고 모든 요청이 5초 안에 다시 성공, 끝난 뒤 풀이 10개로 회복 |
| `outage[-pause\|-stop]` | 낮은 부하(연결 8, 30 req/s) 중 앱 DB 컨테이너를 10초 멈췄다 되살림. `pause`는 `docker pause`/`unpause`, `stop`은 `docker stop`/`start`. `/actuator/health`를 0.5초마다 부른다 | 되살린 뒤 모든 요청이 15초 안에 다시 성공, 헬스체크 UP, 데이터 유지. 중단 중 응답 코드·지연, 헬스체크 상태는 기록 |
| `abort` | `feedbacks` 테이블에 ACCESS EXCLUSIVE 잠금을 걸고(race.rs `pool_exhaustion`처럼) 쓰기 요청 50개를 보낸 뒤 응답 전에 소켓을 닫고, 잠금을 푼다 | 풀·`idle in transaction`·스레드가 정상으로 돌아오고(누수 검사) 서버가 새 요청에 응답. 끊긴 요청이 DB에 실제로 들어간 행 수를 기록(둘 다 취소하지 않고 끝까지 처리한다) |

`pause`와 `stop`의 의미가 다르다. `pause`는 프로세스를 얼려 TCP 연결은 열린 채 응답만 멈춘다(느린 DB·망 정지와 비슷): 질의는 풀린 뒤 이어서 끝난다.
`stop`/`start`는 DB가 종료되어 연결이 모두 끊기고 새 연결이 거부된다(재시작·장애 조치와 비슷): 앱이 죽은 연결을 버리고 새로 맺어야 한다.

### 한도에서 어떻게 실패하는가 (Rust 컨테이너 한도를 낮춰서)

`PERF_APP_NOFILE`, `PERF_APP_PIDS`로 스택을 다시 띄운 뒤 `perf.sh stress rust idle:N`을 돌렸다. 도구는 원인을 가려 적는다.

| 조건 | 결과 |
| --- | --- |
| 앱 nofile 4096, 유휴 5000 | 2205개만 붙음(처음 실패 2024개째). 서버 FD 4096/4096. 새 연결은 RST 71, 응답 시간 초과 19. 도구 판정: "서버 컨테이너 nofile 한도" |
| 앱 pids 1000, 유휴 2000 | 998개만 붙음. 이후 새 연결은 모두 RST. **같은 시간 일반 부하 300개도 전부 실패(RST 285, 응답 없이 닫힘 15)**. 도구 판정: "서버 컨테이너 pids 한도: 1000 / 1000" |
| 부하 발생기 `ulimit -n`이 모자랄 때 | 시작 전에 "부하 발생기 쪽 한도: nofile N < 필요 M"으로 실패 |

Java는 같은 5000 유휴 연결을 FD 5024개, 스레드 223개로 받는다.

## 발견과 조치

아래는 수정 전 발견이다. 조치: 2번 연결당 FD 1개, 3번 유휴 연결은 잠들고 종료 신호로만 깨어남, 4번 요청 줄·헤더 전체 마감(20초, 본문은 바이트마다 연장),
5번 풀 백그라운드 채우기, 1번 스레드를 못 띄우면 503을 돌려주고 로그를 남김(스레드 한도 자체는 구조상 그대로).
6번은 차이로 기록만 한다. 근거와 시험은 [report-2026-10-15-concurrency.md](report-2026-10-15-concurrency.md).

1. **스레드·FD 한도에 닿으면 서버 전체가 요청을 못 받는다.** 연결마다 스레드를 띄우는 구조라 유휴 연결이 스레드 한도(pids, `ulimit -u`, 메모리)를 다 쓰면
   새 연결은 스레드를 못 얻어 RST로 닫힌다(`serve.rs` 117~126행: `spawn` 실패 시 10ms 쉬고 그 연결만 버림. 로그도 안 남는다). 일반 사용자 요청도 새 연결이면 똑같이 실패한다.
   재현: `PERF_APP_PIDS=1000 harness/scripts/perf.sh up; harness/scripts/perf.sh stress rust idle:2000`. Tomcat은 NIO라 유휴 연결이 워커를 안 쓴다.
2. **연결 하나가 FD를 2개 쓴다.** `serve.rs` 285행의 `stream.try_clone()`(읽기·쓰기 핸들) 때문이다. nofile이 같으면 Tomcat(연결당 1개)의 절반 연결에서 막힌다.
   `try_clone`이 `EMFILE`로 실패하면 그 연결은 조용히 닫힌다(285~287행). 재현: `PERF_APP_NOFILE=4096 ... stress rust idle:5000`. Docker 기본 nofile은 이 환경 20000(운영 AWS 환경은 따로 확인).
3. **유휴 연결 수에 비례하는 CPU.** `POLL_SLICE` 100ms마다 모든 유휴 연결 스레드가 깨어난다(`serve.rs` 31행 `POLL_SLICE`, 282행). 측정: 유휴 연결 1000개당 약 0.08코어(5000개 0.39코어,
   앱 컨테이너 한도 2코어의 약 20%). Java는 0. 5000개까지는 판정 한도(0.5코어)를 넘지 않았지만 선형이라 20000개면 한도를 넘는다. 스레드는 5004개, 앱 RSS는 Java(685MB)의 약 1/5(133MB).
4. **느린 클라이언트가 바이트를 조금씩 보내면 끊기지 않는다(Tomcat도 같다).** `PollReader::read`가 바이트를 하나만 받아도 마감을 갱신한다(`serve.rs` 252행). 헤더 8KB 한도까지 가야 끊기므로
   한 바이트를 3초에 보내는 연결은 사실상 영원히 산다(30초 시험에서 300개 모두 유지). Rust에서는 연결 하나가 스레드 하나라 1번의 한도를 소진시키는 데 쓰인다.
   헤더 전체 마감(요청 줄·헤더를 N초 안에 다 못 받으면 408)이 필요하다. Tomcat도 `connectionTimeout`이 읽기마다 갱신되어 같은 약점이 있다(배포는 ALB 뒤라 ALB가 막는지 확인 필요).
5. **끊긴 풀이 필요할 때만 다시 찬다.** `pool.rs` `get`(129행~)은 최소 유휴 연결을 유지하는 일이 없다. DB 연결이 모두 끊긴 뒤 부하가 낮으면 앱 연결이 2~3개로 남고
   (Hikari는 10개로 바로 채운다), 다음 급증에서 연결 맺는 비용이 요청 지연에 얹힌다. 10개 상한은 지켜졌고 누수는 없다.
6. **Java와 다른 응답.** 멈춘 요청 헤더: Rust 408, Tomcat은 응답 없이 닫는다. DB 정지 중 `/actuator/health`: Java가 503 DOWN을 한 번 돌려줬고 Rust는 풀 대기로 막혔다가 UP을 돌려줬다
   (표본이 1~2개라 참고만. 로드밸런서 헬스체크가 DB 장애에 즉시 DOWN을 원하면 확인 필요).

문제 없던 것: 급증·연결 폭주(3000개 동시 연결, 모두 성공, 첫 SYN 재전송 때문에 p50이 1초대)·과부하 공정성(굶는 연결 없음, 꼬리는 Java와 같은 수준)·DB 연결 끊기·DB 중단·클라이언트 중단 모두
오류가 한 자리 수고 모든 요청이 0.1초 안에 다시 성공했으며 `idle in transaction`은 어디서도 0이었다.

## 한계

- 이 실행은 `--quick`이고 호스트가 공유다. 풀 대기 30초 한도(500)를 실제로 넘기는 부하(`fairness`를 느린 DB와 함께)는 돌리지 않았다.
- 앱이 풀 대기 시간을 노출하지 않아 `spike`의 "풀 대기 최대"는 최대 지연(상한)과 풀 포화 비율로 대신한다.
- Hikari/Tomcat 설정은 원본 기본값이다(`maximumPoolSize` 10, `max-threads` 200, `accept-count` 100). 배포 설정을 따로 두었다면 그 값으로 다시 돌려야 한다.
- 운영 환경(AWS Lambda 등)과 같은 구성은 로컬 시험 환경 계획에서 다룬다.
