- 같은 머신, 앱 컨테이너 `cpus: 2` / 1.5GB, 앱마다 전용 PostgreSQL 18.4(`cpus: 1`, tmpfs, `pg_stat_statements`), 풀 10(HikariCP 기본, Rust 기본),

  Java는 워밍업 뒤 측정.
- 측정 중 호스트 부하 평균(1분): 중앙값 66.8, 최소 54.2, 최대 78.6.

## 발견한 문제와 조치

### 1. 유휴 keep-alive 연결이 서버를 멈춘다 (플랫폼, 별도 커밋)

- 증상: 연결 하나가 워커 하나를 붙들던 구조(워커 N개 + 큐)에서 유휴 keep-alive 연결이 워커 수 이상 붙어 있으면 새 요청을 하나도 못 받았다.
  유휴 연결 250개를 붙이고 부하를 주면 **0 req/s**. 브라우저, 앱, 로드밸런서의 풀링 연결이 모두 이 조건을 만든다.
- 원인: `crates/platform/http/src/server/serve.rs`의 워커 풀이 연결 단위로 워커를 점유했다.
- 조치: 연결마다 스레드를 두고, 핸들러 실행 중일 때만 세마포어(허용 수 = `workers`)를 잡도록 바꿨다. `max_connections`는 열린 연결 수 한도가 된다.
  종료는 열린 연결이 0이 될 때까지 기다린다. TDD로 시험 3개를 먼저 추가했다
  (`idle_keep_alive_connections_do_not_starve_new_requests`, `handler_concurrency_is_capped_at_workers`, `shutdown_with_many_idle_connections_is_quick`).
- 전후: 같은 조건(유휴 연결 250개)에서 수정 전 0 req/s, 수정 후 Rust 219 req/s. 같은 조건의 Java는 69 req/s.

### 2. SQL 수 게이트의 오탐 (측정기)

- 처음에 한 엔드포인트가 5.03 대 5.00으로 실패했다. 풀이 연결을 검증하려고 보내는 `SELECT $1`이 센 값에 섞인 탓이다.
  측정기(`harness/loadgen/src/sql.rs`)가 이를 제외하도록 고쳤고 재측정에서 17개 모두 같다.

## 알려진 한계

- 호스트 포화(부하 55~90 / 4코어)로 고정 RPS를 40까지 낮췄다. 절대 지연은 의미가 없고 상대 비교만 본다.
- 엔드포인트별 처리량 실행은 연결 64개 최대 모드라 Java의 JIT 상태에 민감하다. 3라운드 중앙값이며 최소–최대를 함께 적었다.
- 운영 호출 비율이 아직 없어 혼합 비율은 가정이다(`mix.rs`).
- 게시물 작성 완료(`POST /posts`)는 S3 확인이 필요해 부하에서 뺐다.
