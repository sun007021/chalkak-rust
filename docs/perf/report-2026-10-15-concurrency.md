# 동시성·커넥션 풀·트랜잭션 격리 검증 보고서 (2026-10-15)

이슈 #36. 트래픽이 몰릴 때의 동시성, 커넥션 풀 안정성, 트랜잭션 격리를 원본 Java 서버(Tomcat + HikariCP)와 **같은 조건**에서 비교했다.
방법과 명령은 [README.md](README.md), 스트레스 시험 설계는 [stress.md](stress.md). 전체 표는

[tables-before-statement-cache.md](results/2026-10-15/tables-before-statement-cache.md), 트랜잭션 모양 비교는

해석 [txshape-notes.md](results/2026-10-15/txshape-notes.md).

## 결론

- **트랜잭션 격리**: 두 구현 모두 PostgreSQL 기본 READ COMMITTED만 쓰고, 48개 시나리오 1596개 요청에서 쓰기가 다른 트랜잭션으로 나뉜 곳(부분 커밋
  가능성)은 0건이다. 트리거로 트랜잭션 중간을 실패시킨 원자성 시험 8개, 커밋 전 값이 안 보이는지 본 시험 2개, 토큰·가입·탈퇴 경쟁 시험이 Java와
  같은 상태 코드와 같은 DB 최종 상태로 끝났다. 잠금 강도가 원본보다 셌던 두 곳을 원본과 같게 고쳤다.
- **트래픽 급증·풀 안정성**: 15개 스트레스 케이스(급증 50~800 연결, 연결 폭주 3000, 유휴 연결 5000, 느린 클라이언트, 과부하 공정성, DB 연결 강제 종료,
  DB 정지·재시작, 응답 전 클라이언트 끊김)에서 Java와 Rust 모두 통과했다. 오류는 DB를 강제로 끊거나 멈춘 순간의 1~3건뿐이고 둘 다 0.1초 안에
  회복했다. 모든 케이스 뒤에 DB 연결은 풀 크기 10, `idle in transaction` 0, 스레드·FD는 시작 수준이었다.
- **시험 중 찾아 고친 Rust 결함 5가지**(아래 "발견과 조치"). 가장 큰 것은 준비된 문장(prepared statement)을 쓰지 않아 DB가 질의마다 계획을 다시
  세우던 문제다. 고친 뒤 성능 게이트 **통과 53, 실패 0**(고치기 전 같은 호스트에서 실패 7), 엔드포인트별 최대 처리량은 17개 모두 Java보다 높다.
- 한계: 4코어 공유 호스트(측정 중 부하 중앙값 12)에서 잰 값이라 절대 수치보다 번갈아 잰 상대 비교를 본다. 운영(AWS) 구성과 같은 환경 시험은
  로컬 AWS 재현 계획에서 다룬다.

## 비교 조건

- 같은 docker-compose(`harness/perf/compose.yaml`), 앱 `cpus: 2`·1.5GB, 앱마다 전용 PostgreSQL 18.4(`cpus: 1`), 같은 시드, 실제 시계.
- 같은 한도: 풀 10(HikariCP 기본 / Rust 기본), 동시 실행 200(Tomcat `max-threads` / Rust 실행 세마포어), 연결 상한 8192, 풀 대기 30초.
- 성능은 Java/Rust를 라운드마다 순서를 바꿔 3라운드, Java는 워밍업 뒤 측정. 스트레스·동시성 시험은 같은 요청 열을 두 구현에 보낸다.

## 1. 트랜잭션 격리

### 트랜잭션 모양 비교 (`check.sh txshape`, 새 도구)

lane PostgreSQL의 문장 로그(`log_statement=all`)로 요청마다 앱이 보낸 SQL을 트랜잭션 단위로 묶고(시작 방식, 격리 수준, 문장 종류·대상 테이블·잠금,
COMMIT/ROLLBACK), Java와 Rust를 비교한다. 48개 시나리오, 1596개 요청.

| | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 같음 | 1382 | 1490 |
| 동등(설명 가능한 차이) | 85 | 98 |
| 다름 | 129 | 8 |
| 격리 수준 차이 | 0 | 0 |
| 쓰기가 다른 트랜잭션으로 나뉨(원자성 차이) | 0 | 0 |

- **고친 다름 121건**: 회원·대기 중인 Apple 인증 행 잠금이 Rust `FOR UPDATE`, 원본 `FOR NO KEY UPDATE`였다. `FOR UPDATE`는 외래 키 검사의
  `FOR KEY SHARE`와 충돌해서, 회원 행을 잠근 트랜잭션(탈퇴, 사인 등록, 관리자 상태 변경) 동안 그 회원의 좋아요·게시물·알림 INSERT가 기다렸다
  (원본은 기다리지 않는다). 게시물 잠금 조회는 Rust가 사진 행까지(`OF p, ph`), 원본은 게시물 행만(`of p1_0`) 잠갔다. 둘 다 원본과 같게 바꾸고
  잠금 대기를 확인하는 DB 시험 7개(`crates/app/src/admin/lock_db_tests.rs`)를 먼저 썼다.
- **남은 다름 8건**은 모두 결과가 같다: 400으로 롤백되는 요청에서 Rust가 UPDATE를 보낸 뒤 롤백(원본은 flush 전 예외), 알림 읽음 404에서 원본만
  0행 UPDATE를 롤백, 탈퇴에서 Rust가 0행일 수 있는 `DELETE apple_authorizations`를 항상 보냄. 해석은 [txshape-notes.md](results/2026-10-15/txshape-notes.md).
- **동등**: 읽기 전용 요청에서 원본은 `BEGIN READ ONLY`로 SELECT 여러 개를 묶고 Rust는 자동 커밋으로 보낸다. READ COMMITTED에서는 문장마다 새
  스냅샷이라 응답이 같다(하네스 응답 비교 48/48 일치). 한 요청 안의 여러 SELECT가 같은 시점을 보는 보장은 원본도 없다.
- 전체 실행에서 한 번 `user__signature-callbacks`의 응답·DB가 다르게 나왔으나, 같은 시나리오를 `compare`로 1번, `txshape`로 2번 다시 돌려 모두
  일치했다. 공유 호스트 부하로 lane 시계가 흔들린 것으로 본다(추정).

### 격리·원자성 경쟁 시험 (`perf.sh race`, 19개 추가, 기존 13개 포함 32개)

같은 시험을 Java와 Rust에 보내 상태 코드 분포와 DB 최종 상태를 대조한다(`report`의 "Java 대 Rust 대조" 표).

| 묶음 | 시험 | 결과 |
| --- | --- | --- |
| 원자성 | 관리자 검수(알림·감사 로그 실패), 관리자 삭제, 작성자 삭제, 탈퇴, 회원·관리자 리프레시 회전, 관리자 차단: 뒤쪽 테이블에 `RAISE EXCEPTION` 트리거 | 8개 모두 Java·Rust 500, 앞쪽 변경이 남지 않음, 트리거를 지우고 다시 하면 성공. DB 상태 같음 |
| 커밋 전 값 | 쓰기 트랜잭션 안에 `pg_sleep(2)` 트리거를 걸고 그동안 GET | 둘 다 진행 중엔 예전 값, 커밋 응답 뒤엔 새 값 |
| 토큰 경쟁 | 같은 리프레시 토큰 20개 동시(회원·관리자) | 둘 다 `200 1, 401 19`, 계보 전체 폐기 |
| 가입 경쟁 | 같은 가입 토큰 10개, 같은 신원 다른 토큰 4개 | 둘 다 회원 1명. 같은 신원은 둘 다 `200 1, 500 3`(유일 제약 위반, 원본과 같음) |
| 잠금 순서 | 탈퇴 12개 동시 × 3, 탈퇴 대 리프레시, 좋아요 대 작성자 삭제, 차단 경쟁 | 교착 없음, 5xx 없음, 고아 좋아요 0 |

**알려진 차이 1건**: 같은 회원의 탈퇴 12개를 동시에 보내면 원본은 4~9건이 500이다(Hibernate가 이미 지워진 `social_accounts` 행을 엔티티 단위로
다시 지우다 `StaleStateException`). Rust는 집합 삭제라 204/401만 나온다. 최종 DB 상태는 같다. 원본의 결함으로 보고 Rust 동작을 유지했다.

## 2. 트래픽 급증과 커넥션 풀 (`perf.sh stress`, 새 도구)

최종 측정(문장 캐시 반영 뒤). Java 값은 같은 호스트의 직전 실행이다.

| 케이스 | Java | Rust |
| --- | --- | --- |
| 급증 50 / 200 / 400 / 800 연결: 급증 중 p99 | 0.38 / 1.26 / 2.06 / 3.51초 | 0.11 / 0.49 / 0.80 / 1.70초 |
| 급증 뒤 평소 지연으로 돌아오기까지 | 0~1초, 오류 0 | 0초, 오류 0 |
| 연결 폭주 1000 / 3000(keep-alive 없이 동시에) | 모두 성공, 1.2 / 2.3초 | 모두 성공, 1.5 / 2.8초 |
| 유휴 keep-alive 5000개: 유휴 CPU, RSS, 스레드, FD | 0.00코어, 811MB, 223, 5025 | 0.00코어, 137MB, 5002, 5046 |
| 느린 클라이언트 400(멈춘 100 + 3초에 1바이트 300) | 멈춘 연결 60초에 닫음, 1바이트씩은 안 끊김 | 멈춘 연결 21초에 408, 1바이트씩도 20초에 끊음 |
| 과부하 공정성 400 / 1000 연결, DB 쓰는 엔드포인트만 | p99.9 1.8 / 4.4초, 500 0 | p99.9 1.1 / 1.7초, 500 0 |
| 연결별 완료 수 최소/중앙(굶는 연결 확인) | 43/68, 16/29 | 218/250, 72/95 |
| DB 연결 강제 종료 3회(부하 중) | 오류 2·2·2, 회복 0.0초 | 오류 1·1·3, 회복 0.0~0.1초 |
| DB 10초 pause / stop | 오류 0 / 3, 헬스체크 503 1회 | 오류 0 / 1, 헬스체크 503 없음(풀 대기 중 DB가 돌아옴) |
| 응답 전에 소켓을 닫은 요청 50개 | 50개 모두 끝까지 처리, 누수 없음 | 같음 |

- 풀 대기 30초 한도를 넘기는 경우(`pool-exhaustion-timeout`, 테이블 잠금으로 풀을 묶음)는 둘 다 500을 돌려주고 잠금이 풀리면 회복한다.
- 연결 폭주에서 Rust가 조금 느린 것은 연결마다 OS 스레드를 만드는 비용이다(3000개 2.8초 대 2.3초). 실패는 없다.
- Rust는 유휴 연결 하나가 스레드 하나다(Tomcat은 NIO라 스레드를 안 쓴다). 수정 뒤 유휴 스레드는 CPU를 쓰지 않고 FD도 연결당 1개지만, 컨테이너
  pids 한도가 낮으면 스레드 수가 먼저 막힌다(`PERF_APP_PIDS=1000`에서 유휴 연결 약 1000개). 배포할 때 pids 한도를 연결 상한 이상으로 둔다.

## 발견과 조치

| # | 문제 | 근거 | 조치 | 확인 |
| --- | --- | --- | --- | --- |
| 1 | DB가 질의마다 계획을 다시 세운다. `postgres`의 `query(&str)`는 매번 이름 없는 문장을 만든다. 게시물 상세 4중 조인은 계획 1.5ms·실행 0.14ms, Rust DB CPU가 요청당 Java의 2.2배였고 DB 1코어가 막혀 처리량이 Java의 60%였다 | `pg_stat_statements.track_planning`: Rust plans 24038회 9.4초, Java 0회. DB 컨테이너 CPU 제한 걸림(Rust 90회, Java 2회) | 연결별 준비된 문장 캐시(`chalkak_db::StatementCache`, 256개). 앱은 `impl Db`·`Tx`를 받는다. pgjdbc의 준비된 문장 재사용과 같은 효과 | 시험 3개, 게이트 실패 7 → 0 |
| 2 | 잠금이 원본보다 세다(`FOR UPDATE`, 사진 행 잠금) | txshape 다름 121건 | `FOR NO KEY UPDATE`, `OF p` | 잠금 대기 시험 7개, txshape 다름 8건(결과 같음) |
| 3 | 유휴 keep-alive 연결 스레드가 100ms마다 깨어난다(1000개당 0.08코어) | stress idle: 5000개에 0.39코어 | 마감까지 남은 시간을 읽기 제한으로 걸고 잠든다. 종료 신호는 유휴 목록의 읽기 쪽을 닫아 깨운다 | `/proc` 깨어남 수 시험, 5000개 0.00코어 |
| 4 | 연결 하나가 FD 2개(`try_clone`), 스레드를 못 만들면 조용히 RST | 5000 연결에 FD 10050, pids 한도에서 RST | `Arc<TcpStream>`으로 FD 1개, 스레드 생성 실패는 503 | FD 수 시험, 5000 연결 FD 5046 |
| 5 | 헤더를 한 바이트씩 보내면 바이트마다 마감이 늘어 끊기지 않는다(연결이 스레드를 붙잡는 수단) | stress slow: 300개 모두 유지 | 요청 줄·헤더는 첫 바이트부터 `read_timeout`(20초) 안에, 본문은 지금처럼 바이트마다 연장 | 시험 2개, 300개 모두 끊김 |
| 6 | DB 연결이 끊기면 풀이 필요할 때만 다시 맺는다(Hikari는 백그라운드로 채움) | stress dbkill: 저부하에서 2~3개로 남음 | 연결을 버리는 순간 백그라운드 채우기(재시도 250ms~5초) | 시험 4개 |

6번의 남은 차이: 강제 종료된 연결이 **아직 풀에 있는 줄 모르는** 동안(유휴 연결 중 최근에 안 쓴 것)은 채우기가 시작되지 않는다. Rust 풀은 마지막에
돌려받은 연결부터 빌려 주므로(LIFO) 저부하에서는 몇 개만 돌고, 나머지 죽은 연결은 다음 급증 때 빌릴 때 검사(`is_valid`, 쉰 지 500ms 넘은 연결)로
걸러져 그 자리에서 다시 맺는다. 사용자 오류로 이어지지는 않고(검사에서 걸러진다) 첫 요청 몇 개에 연결 비용이 얹힌다. 강제 종료 시험에서 오류·회복
시간은 Java와 같은 수준이었다.
