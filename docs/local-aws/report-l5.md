# L5 로컬 AWS 안정성 시험 보고 (2026-10-19~20, 이슈 #56)

계획 7.2의 S1~S6·S8·S9를 로컬 AWS 스택(`local-aws/compose.yaml` + `compose.l5.yaml`)에서 **같은 DB 시드·같은 시나리오로 Rust와 Java(원본 JAR, 기준 9c33014)에 두 번씩** 돌려 대조했다.
S7(푸시 경로)은 별도 보고 [`report-s7.md`](report-s7.md). 환경은 클라우드 세션 컨테이너(공유 4코어, 메모리 16GB)다.

## 재현

```bash
# 사전 준비는 local-aws/README.md 의 빠른 시작과 같다(fetch-tools.sh, prepare-lambda.sh,
# cargo build --release -p chalkak-fakes -p chalkak-server -p chalkak-loadgen, Java 는 /tmp/chalkak-lanes/oracle/app.jar)
cd local-aws
scripts/l5.sh rust                    # S1 S2 S3 S6 S8 S5 S4 순서로 전부(약 1시간 40분). 시작 시 down -v → up → 시드, 끝나면 down -v
scripts/l5.sh java                    # 같은 시나리오를 원본 JAR 로
scripts/l5.sh rust S2 S3              # 일부만 (S1_MINUTES=2 로 S1 을 짧게, KEEP=1 로 스택 유지)
scripts/l5.sh compare S1 S2 S3 S4 S5 S6 S8   # 가장 최근 rust·java 결과를 나란히 놓고 A/B 판정(종료 코드 0 이면 통과)
scripts/s9.sh rust --duration 1h --static-credentials --out .state/s9/rust-1h-static   # S9 1시간 예비
scripts/s9.sh rust --duration 8h --static-credentials                                   # S9 본 실행(약 8시간)
scripts/s9.sh judge .state/s9/<디렉터리>    # 이미 있는 출력 파일만으로 다시 판정
```

### S1 정상 부하 30분: 통과
| 항목 | Rust | Java |
| --- | --- | --- |
| 5xx (loadgen·edge 접근 로그) | 0 / 0 | 0 / 0 |
| p99 (loadgen) | 8.5 ms | 70778.9 ms |
| p99 (edge 접근 로그, 전체) | 7.57 ms | 1156.55 ms |
| p50 (edge) | 1.6 ms | 142.66 ms |
| 풀 대기 | pending 최대 0 (0/30 표본), active 최대 1 | pending 최대 22 (3/8 표본, 연속 2), active 최대 10 |
| RSS | 13.5 → 14.2 MB (기울기 1.8 MB/h) | 1343 → 1359 MB |
| 스레드 / FD 최대 | 31 / 59 | 93 / 74 |
| 업로드 540건 | 540 READY, 반려·오류 0, 콜백 대기 p99 0.77 s | 540 READY, 콜백 대기 p99 4.2 s |

- Rust는 모든 기준을 통과하고 p99가 Java 이하다. loadgen은 목표 RPS를 고정해 쏘는 방식이라 서버가 한 번 밀리면 대기 시간이 쌓여 보이므로(Java loadgen p95 65 s) 서버 쪽 지연인 edge 접근 로그 p99(Java 1.16 s)를 함께 적는다. 둘 다 Rust가 작다. Java 쪽 원인은 풀 대기 연속 발생과 JVM 워밍업, 공유 호스트 경쟁으로 짐작하며 분리해 확인하지는 않았다.
- 처음 Rust 실행(`rust-S1-20261019-193218`)은 풀 대기 최댓값 25가 한 번 찍혀 "풀 고갈 없음"이 실패였다. 당시 기준은 "pending > 0 한 번이라도"였다. 분 경계 작업이나 호스트 정지로 순간 대기가 한 표본 튀는 것은 풀 고갈이 아니고 Java도 같은 값을 보였다(pending 22). 그래서 커밋 92f6366에서 기준을 "1분 표본이 연달아 2번 이상 pending > 0 이거나 대기 시간 초과 오류"로 바꿨다. 기준을 바꾼 뒤 Rust를 다시 돌렸고 대기 표본은 0/30이다. 첫 실행은 다른 작업자가 CPU를 쓰던 때였다.
- Java는 새 기준에서도 풀 대기가 연속 2번 나와 이 항목이 실패다(HikariCP 풀 10, 원본 설정). 원본 쪽 관찰이며 고치지 않는다.

### S3 콜백 중복·역순: 통과
28개 기준(단계별 상태 코드·DB 상태·오류 본문) 모두 통과이고 `compare`의 단계별 대조는 **차이 0건**이다.
- 같은 complete 재전송 2번, 완료 뒤 늦은 failed: 모두 204, 상태·`updated_at` 불변(상태 변화는 처음 1회뿐).
- failed(TOO_LARGE) 뒤 늦은 complete: 204, REJECTED 유지·메타데이터 없음. 다른 사유 failed: 첫 사유 유지.
- 모르는 uploadId: 204. 잘못된 서명·10분 지난 타임스탬프·다른 환경 서명: 401. 형식이 틀린 id·본문 없는 failed: 400. 오류 본문까지 같다.
- esm-poller가 같은 SQS 메시지를 두 번 전달: 상태 불변, 메시지 모두 삭제, 큐 비어 있음.

IMDS 모드에서 실패한 4개는 imds-mock이 자격증명 `Expiration`을 2020년으로 내놓아 SQS·S3 호출마다 IMDS를 다시 부르고, 호스트가 바쁠 때 그 호출이 연결 거부로 실패하기 때문이다(`transport error: 연결 실패: Connection refused`). 그 결과 5xx 5건, ERROR 5줄, SQS 연결 오류 140줄, 주제 푸시 일부 미수락이 나왔다. 실제 AWS의 IMDS는 `Expiration`이 몇 시간 뒤라 호출마다 부르지 않는다. 정적 자격증명 모드는 이 잡음을 빼고 같은 시험을 하는 선택지(`compose.s9-static.yaml`)이며, 이 모드에서는 연결 오류·미수락 0을 통과 조건으로 건다.

8시간 본 실행(`scripts/s9.sh rust --duration 8h --static-credentials`)은 이 이슈 범위 밖이라 하지 않았다. 10분 정적 실행(`static10m`)은 p99 증가 기준만 실패한 적이 있어(앞 142.8 ms, 뒤 1282.5 ms, 다른 작업이 CPU를 쓰던 때로 보인다), 본 실행은 다른 작업이 없는 때 돌려야 한다.

## 4코어 공유 호스트의 한계
- 이 컨테이너는 4코어를 다른 작업자와 나눠 쓴다. 호스트 부하 평균이 20~40까지 올라간 시간대가 있었다(S9 예비 실행 기록). 그래서 **절대 수치(ms)는 AWS의 값이 아니고**, 같은 시각 근처에서 번갈아 돈 Rust↔Java의 상대 비교와 "기준 통과 여부"만 의미가 있다. 첫 Rust S1 풀 대기 표본, 10분 S9 p99 증가가 그런 호스트 잡음으로 보인다.
- S1~S5는 호스트 한 대 안에서 backend·postgres·LocalStack·Lambda 컨테이너 4개·edge·loadgen이 같은 CPU를 쓴다. 부하 발생기와 서버가 CPU를 다투므로 Rust의 이점(적은 CPU)은 작게, Java의 JVM 워밍업과 GC 영향은 크게 보일 수 있다.
- Lambda는 컨테이너 4개(esm-poller 동시 4)라 S2 업로드 몰림의 처리 시간은 서버가 아니라 Lambda 용량이 정한다. 실제 AWS의 Lambda 동시성과 같지 않다.
- S6은 시험 시간을 줄이려고 큐 visibility를 360초 → 10초로 줄였다(재시도 상한 5회는 그대로). 끝나면 360초로 되돌린다. S4의 재전달 대기는 실제 360초를 기다린다.
- S9 8시간은 호스트가 비어 있을 때만 의미가 있다. 다른 작업과 겹치면 p99·스레드 기준이 흔들린다.
- 실제 AWS(S3 지연·SQS 가시성·RDS 페일오버·네트워크)와의 차이는 #32 배포 뒤 같은 시나리오(`l5.sh`, `s9.sh`)를 다시 돌려 확인한다.
